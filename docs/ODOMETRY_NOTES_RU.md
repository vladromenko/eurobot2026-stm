# Энкодеры, TPM и кинематика: как устроено движение робота

Разбор кода движения и одометрии в прошивке (`main`, 28.10.2026). Все ссылки на строки относятся к коммиту `55b23dd`.

**Главное:**
- Скорость моторов Maxon задаётся и читается в **TPM — тиках энкодера в минуту**.
- Пересчёт «скорость робота ⇄ TPM трёх моторов» делается в `Core/App/kinematics.c` двумя матрицами 3×3.
- При переносе на GCC/CMake **пропали откалиброванные параметры одометрии** (см. раздел 7). Это нужно проверить в первую очередь.

## 2. Энкодер

Энкодер — это датчик поворота вала. У нас он стоит на валу каждого мотора Maxon, **до редуктора**.

- На валу закреплён диск с прорезями или магнит. Датчик выдаёт импульс, когда мимо проходит метка, — это **тик**.
- Каналов два, A и B, они сдвинуты на четверть периода (квадратурный сигнал). По тому, какой канал меняется первым, контроллер определяет направление вращения. Вперёд тики прибавляются, назад — вычитаются.
- `ENCODER_TICKS_PER_TURN = 4096` — число тиков на один оборот вала мотора. Вероятно, это 1024 метки × 4 фронта, но это надо сверить с даташитом мотора.
- Энкодер **инкрементальный**: он не знает абсолютного положения, только сколько тиков прошло с момента включения или сброса.

Для чего он нужен:

| Задача | Как работает | Где в коде |
|---|---|---|
| **Регулирование скорости** | STM32 отправляет задание `Set_TPM`. PID-регулятор контроллера Maxon сравнивает его с фактической скоростью по энкодеру и подстраивает ШИМ. | `Odometry.SetSpeed` → `odometry.c:65-75` |
| **Чтение скорости** | `Get_TPM` возвращает фактическую скорость мотора. | `odometry.c:78-87` |
| **Одометрия** (где робот) | Накопленный счётчик `GetTotalTicks` → путь каждого колеса → смещение робота. | `odometry.c:89-112` |

## 3. TPM — тики в минуту

TPM — это скорость вращения вала мотора в тиках энкодера за минуту:

```
TPM = (об/мин мотора) × 4096
```

По смыслу это те же обороты в минуту, но с разрешением в 4096 раз выше. Скорость передаётся контроллеру как `int32_t`, и мелкая единица позволяет задавать малые скорости без дробей.

> ⚠️ В `Core/Lib/Include/maxon.h:33,36` регистры подписаны как «Ticks Per **Second** (TPM)». Формула в `kinematics.c` считает именно тики в **минуту** (множитель 60). Какая единица правильная, определяет прошивка контроллера Maxon, а её в репозитории нет. Если робот едет в 60 раз быстрее или медленнее, чем задано, причина здесь. Иначе просто неверен комментарий.

## 4. Параметры робота

`Core/App/kinematics.c:31-34`:

| Константа | Значение в `main` | Смысл |
|---|---|---|
| `DIST_CENTER_TO_WHEEL_m` (L) | 0.1075 м | Расстояние от центра робота до колеса |
| `WHEEL_RADIUS_m` (r) | 0.03 м | Радиус колеса |
| `GEAR_RATIO` | 21 | Передаточное число редуктора: сколько оборотов мотора приходится на 1 оборот колеса |
| `ENCODER_TICKS_PER_TURN` | 4096 | Тиков на оборот вала мотора |

Энкодер стоит до редуктора, поэтому:

- на один оборот колеса приходится `GEAR_RATIO × 4096` = 86 016 тиков;
- один оборот колеса — это путь `2πr` ≈ 0,188 м;
- один тик ≈ **2,2 мкм** пути колеса (`ticks_to_m`).

Коэффициент м/с → TPM (`kinematics.c:65`):

```c
ms_to_tpm = (30·GEAR_RATIO) / (π·r) · 4096
//        = v / (2πr) · 60   → об/мин колеса
//          × GEAR_RATIO     → об/мин мотора
//          × 4096           → тиков/мин
```

При текущих параметрах 1 м/с колеса ≈ **27,4 млн TPM**.

## 5. Кинематика: скорость робота ⇄ скорости колёс

Робот трёхколёсный, на omni-колёсах, расположенных через 120°. Скорость робота задаётся структурой `speed_s { dx, dy, dphi }` в системе координат робота (м/с, м/с, рад/с).

### `SpeedTo_TPM`: скорость робота → TPM моторов (`kinematics.c:91-105`)

1. **Обратная кинематика.** `arm_direct_matrix` × (dx, dy, dphi) даёт линейные скорости колёс в м/с:
   ```
   v1 =  cos30·dx + cos60·dy + L·dphi
   v2 = −cos30·dx + cos60·dy + L·dphi
   v3 =            −1·dy     + L·dphi
   ```
   Член `L·dphi` — вклад вращения робота. Множитель L добавляется к матрице в `MatrixInit`.
2. Каждое `v` умножается на `ms_to_tpm` и записывается в `int32_t`. Дробная часть отбрасывается, но 1 TPM ≈ 4·10⁻⁸ м/с, так что это не важно.

### `TPM_ToSpeed`: TPM моторов → скорость робота (`kinematics.c:107-120`)

Обратный порядок: TPM / `ms_to_tpm` → м/с колёс → `arm_inverse_matrix`:

```
dx   = (v1 − v2) / √3
dy   = (v1 + v2 − 2·v3) / 3
dphi = (v1 + v2 + v3) / (3·L)
```

Если подставить формулы из `SpeedTo_TPM`, получаются ровно исходные dx, dy, dphi. Значит, матрицы взаимно обратны.

### `UpdatePath`: одометрия (`kinematics.c:123-149`)

Та же обратная матрица, но на входе **приращения тиков** с прошлого шага, переведённые в метры через `ticks_to_m`. Получается смещение (dx, dy, dφ) в системе координат робота. Оно поворачивается на текущий угол `phi` и прибавляется к глобальной позиции `path`.

### Как работают матрицы CMSIS-DSP

Почему кажется, что `ms_matrix` заполняется, но нигде не используется:

```c
float ms[3];
arm_mat_init_f32(&ms_matrix, 3, 1, ms);                        // ms_matrix.pData = ms
arm_mat_mult_f32(&arm_direct_matrix, &speed_matrix, &ms_matrix); // результат пишется в ms[]
tpm[0] = ms[0] * ms_to_tpm;                                    // читаем уже заполненный ms
```

`arm_matrix_instance_f32` — это только описание: `{numRows, numCols, float *pData}`. Своих данных у него нет. Результат умножения записывается по указателю `pData`, то есть прямо в массив `ms`. Так же `speed_matrix` указывает на структуру `speed`: её три `float` идут подряд и читаются как вектор 3×1.

## 6. Производительность

Математика уже ускорена:
- аппаратный FPU (`-mfpu=fpv4-sp-d16 -mfloat-abi=hard`);
- CMSIS-DSP: оптимизированные `arm_mat_mult_f32` и табличные `arm_sin_f32`/`arm_cos_f32`.

Матрица 3×3 на вектор — это доли микросекунды. Узкое место в другом: за один шаг одометрии (100 Гц) происходит три последовательных запроса `GetTotalTicks` по UART/Dynamixel, и каждый ждёт ответа до 2 мс. Если нужно ускорить цикл, начинать стоит с шины: `BulkRead` вместо трёх отдельных `Read` или более высокий baudrate.

Если хочется оптимизировать и математику (выигрыш порядка микросекунд):
- собирать `Drivers/CMSIS/DSP/*` с `-O2` даже в Debug, потому что сейчас в Debug везде `-O0`;
- записать формулы 3×3 явно, без вызова `arm_mat_mult_f32`.

## 7. Найденные проблемы

### 7.1 ❗ При переносе на GCC/CMake пропала калибровка одометрии

Коммит `3d7f02d` (*Port Eurobot 2025 firmware to GCC and CMake*, 27.10.2026) заменил `kinematics.c` и `odometry.c` более старой версией. Потерялась работа, сделанная с апреля по май 2026 (`2a69e8e` … `051934d`, *fix: odometry params for new wheelbase*).

| Параметр | Было (`051934d`) | Сейчас в `main` |
|---|---|---|
| `DIST_CENTER_TO_WHEEL_m` | 0.1217 | 0.1075 |
| `WHEEL_RADIUS_m` | 0.0295 | 0.03 |
| `GEAR_RATIO` | 28 | 21 |
| Калибровочные коэффициенты | `ODOMETRY_CALIBRATION_COEF`, `WHEEL_n_ODOMETRY_COEF` и др. | нет |

Если робот физически тот же, что в мае, одометрия на `main` будет заметно врать: только из-за редуктора путь окажется завышен примерно в 1,33 раза. Нужно решить, какие параметры верные, и при необходимости вернуть изменения:

```bash
git diff 051934d HEAD -- Core/App/kinematics.c Core/App/odometry.c
```

### 7.2 Единицы TPM в `maxon.h`

Комментарий говорит «тики в секунду», формула считает тики в минуту (раздел 3). Нужно сверить с прошивкой контроллера Maxon и исправить либо комментарий, либо формулу.

### 7.3 Плавающий период задачи одометрии

В `Core/OS_Tasks/odometry_task.c:60` строка `xLastWakeTime = xTaskGetTickCount()` стоит **внутри** цикла. Из-за этого `xTaskDelayUntil` работает как обычный `vTaskDelay`, и период получается 10 мс + время UART-обмена (до ~6 мс), а не ровно 10 мс. На одометрию это почти не влияет, потому что она считает по приращениям тиков. Но для стабильной частоты эту строку надо перенести перед `while(1)`.
